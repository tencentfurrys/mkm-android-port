3 OPEN ISSUES (all seen live on A16, Stage2-Beach, P2b build)

[1] GAMEPAD BUTTONS OVERLAP (screenshot confirmed)
Right cluster overlaps: USE button drawn on top of INT; SKL half off right screen edge. Cause: MKM_TouchUI.cs Build() right-cluster coordinates pack 6 buttons into too small an area at this aspect (1920x1080 design scaled s=1.0 on 2340x1080). INT and USE get near-identical centers; SKL x exceeds screen width.
Fix: re-space the cluster in MKM_TouchUI.cs Build() - 2 columns x 3 rows grid anchored bottom-right with margins verified against Screen.width, e.g. col centers at (w - 150*s, w - 320*s), row centers at (180*s, 350*s, 520*s); assign ATK/JMP/INT/SKL/DEF/USE to grid cells; clamp every center to [rad, w-rad]x[rad, h-rad]. Tune with one screenshot round-trip.
Also: pause button (top-right) overlapped a red game icon - move to top-LEFT or below the item HUD.

[3] CHARACTER STUCK RUNNING FORWARD + top-left NRE (screenshot confirmed)
Two possibly-linked symptoms: (a) Maya runs right on her own; (b) diag overlay shows repeating NullReferenceException in UPDT_UINavigation.
Evidence: NRE text "UPDT_UINavigation () (at <000...>" repeats every frame even in gameplay with no menu open. Stuck-run means movHackRight or held-Right latched true.
Suspects, in order:
  (i) Touch state stuck: Btn.OnPointerUp missed (finger released over another UI element / canvas hidden mid-press / scene changed mid-press) leaving MKM_Touch held[Right]=true forever. OnDisable releases only its own button - a pointer stolen by a different control never fires OnPointerUp. Harden: in MKM_TouchUI.Update, each frame verify each pressed button's pointerId is still in Input.touches; if its touch ended/canceled with no OnPointerUp, force Release. Also clear all on Application focus loss (OnApplicationFocus(false) -> ResetAll) and on canvas hide (already ResetAll - confirm it runs).
  (ii) UPDT_UINavigation NRE itself: GameCore ~3771-3812 - EventSystem.current?.currentSelectedGameObject chain or selectable.FindSelectableOn* on a destroyed/ripped object; runs every frame in stages (guard `currentSelectedGameObject?.activeInHierarchy != true` should skip... unless EventSystem.current is null in a way that still enters). Get the FULL stack trace first (see below) - the truncated overlay hides the throwing line.
  (iii) If stuck-run persists with touch UI hidden: check _movHackRight writers (GameCore OnGUI 3835-3882) - keyboard-event branch only runs when isKeyboardCfgInput; a stuck KeyDown without KeyUp (lost focus) latches it. Same focus-loss reset covers it.
How to nail it: pull the FULL MKMDiag.log from the device (persistentDataPath/MKMDiag.log, same folder the earlier logs.zip came from) - it captures every LOG-Exception with stack trace. The throwing line + the last TOUCH markers before the runaway identify it exactly. Do NOT guess further without that file.
